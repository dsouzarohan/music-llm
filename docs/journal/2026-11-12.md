# 2026-11-12

Phase 2, T3–T5 results: the batched-attention and KV-cache measurements at the 186M shape, and the
five ~30M block ablations. All runs on a Colab A100 40GB (2026-11-08 session, with run 1 resumed
from epoch 34 after the VM was reclaimed). T5 run directories: `data/runs/2026-11-08/` on Drive
(`metrics.jsonl` and `config.json` copied locally).

## T3: batched SDPA attention, 186M baseline shape

Eager profile, micro-batch 2, 10 micro-steps (the baseline's setup), plus compiled throughput at
micro-batch 4, epoch 1:

| | Attention forward, 10 eager steps | Eager tok/s (MFU) | Compiled tok/s (MFU) |
|---|---|---|---|
| Baseline (per-head loop) | ~1,615 ms | — (1.7%) | 22.2k (11.0%) |
| Huang, batched SDPA | 749 ms (2.2× less) | 12.3k (6.1%) | 31.9k (15.8%) |
| RoPE | 125 ms (13× less) | 25.4k (10.7%) | **101.8k (43.0%)** |

- Batching the heads alone makes Huang 1.44× faster end to end, with the same maths: 288 small
  per-head launches per layer stack become 24 batched ones.
- RoPE's attention forward costs a sixth of Huang's. With no additive bias, SDPA uses its flash
  kernel and never builds the `(B, H, T, T)` mask. Part of RoPE's overall 4.6× is the smaller model
  (147M vs 186M: no `rel_bias`, no position table).
- **The "% of device time" figures from `profile_report` were wrong** (#27, fixed): torch 2.14
  counts each kernel twice and adds GPU-side annotation spans, so the report said "device busy
  300% of wall" and every share was understated by 2–3×. That includes the baseline's "attention
  is 38% of GPU time" and "busy 32%" (2026-11-08). The absolute region times above don't use the
  broken total, so the comparison holds.

## T4: KV cache

One 512-token sample (64-token prompt), 186M shape, A100:

| | KV cache | no cache |
|---|---|---|
| Huang | 11.5 s | 13.0 s |
| RoPE | 12.8 s | 12.7 s |

The drop from ~108 s to ~12 s comes from T3's batched heads, not from the cache. At batch 1 and
under 600 tokens, each step is so little arithmetic for an A100 that its ~23 ms goes to Python and
kernel launches; the cache only removes arithmetic. On the Mac (MPS, random-init 186M shape, 256
new tokens) it gave ~3× (Huang 8.5 → 2.6 s), and it should matter on the GPU at longer contexts or
bigger sample batches.

## T5: block ablations at ~30M

Same shape (8L/512/8H, context 2048), dropout 0.1, batch 64 (micro 16), peak LR 3e-4 OneCycle,
50 epochs × 2000 windows = 204.8M tokens each, fixed val set. Throughput is the median over epochs.

| Run | Params | Train loss | **Val loss (ppl)** | Δ val | tok/s | MFU |
|---|---|---|---|---|---|---|
| Baseline 186M (2026-11-08), old block | 186.4M | | 3.498 (33.1) | | 22.2k | 11.0% |
| 1. old block (huang, layernorm, gelu, untied) | 34.0M | 2.439 | 2.684 (14.65) | | 152k | 14.0% |
| 2. + RoPE | 24.6M | 2.061 | 2.518 (12.41) | −0.166 | 513k | 39.0% |
| 3. + RMSNorm, QK-norm | 24.6M | 2.045 | 2.476 (11.89) | −0.042 | 464k | 35.3% |
| 4. + SwiGLU | 24.6M | 1.811 | 2.354 (10.52) | −0.122 | 460k | 35.0% |
| 5. + tied embeddings (full modern block) | 22.8M | 1.839 | **2.323 (10.21)** | −0.031 | 462k | 35.1% |

**Chosen block: run 5**, the lowest val loss at the fewest parameters. RMSNorm/QK-norm cost ~10%
throughput against run 2 (more small kernels at this width), but each later step improved val loss
by more than that would buy. `hyperparameters.py` and `MusicTransformer` now default to it;
`colab-186m-jan2026.toml` and `ablation-30m-1-old.toml` pin the old block.

Two separate effects:

1. **Training settings: 3.498 → 2.684** with the old block at a sixth of the size. Run 1 differs
   from the baseline in peak LR (3e-4 vs 1e-4), optimizer steps (1,600 vs 800 at batch 64 vs 128)
   and weight decay (no longer on embeddings, norms and `rel_bias`, #22). The likeliest reading is
   that the baseline was undertrained. These runs change the three together, so they don't say how
   much each contributes.
2. **Block: 2.684 → 2.323** with everything else equal. RoPE (−0.17) and SwiGLU (−0.12) are most of it.

**Overfitting: starting, not yet.** Val loss improved every epoch in every run, but the val − train
gap grows (run 5: −0.05 at epoch 5, 0.24 at 15, 0.42 at 25, 0.53 at 45, 0.48 at 49). Train loss
includes dropout, so the real gap is a bit larger. 204.8M tokens is ~4.8 passes over the ~43M
training tokens, and those include pitch-shifted copies of the same songs. T6 repeats the data
~30×, so it should show where this turns into val loss rising.

Perplexity is per BPE token (vocab 3500), so these numbers only compare across models with this
tokenizer.
