# 2026-11-12

Phase 2 results, from one long Colab A100 session that started on 11-08 (with one VM reclaimed
halfway, and run 1 resumed from epoch 34). Lightning still can't create Studios, so everything ran
on Colab and Lightning moves to Phase 3.

Three things got measured: the new attention code, the KV cache, and five small models comparing
the old block with the modern one.

### Faster attention

The old attention ran each of the 12 heads separately in a Python loop. The new code runs all heads
in one call to PyTorch's `scaled_dot_product_attention` (SDPA). With RoPE, SDPA can also use its
fused "flash" kernel, which never builds the full 2048 × 2048 score matrix in memory.

At the baseline's 186M shape, compiled:

- Old per-head code: 22.2k tokens/s
- Same Huang maths, heads batched: 31.9k tokens/s, **1.44× faster** just from batching
- RoPE: 101.8k tokens/s, **4.6× faster**, MFU 43%

In the uncompiled profile, attention's forward pass went from ~1,615 ms (old) to 749 ms (batched
Huang) to 125 ms (RoPE) over the same 10 steps.

While doing this we found the profiler report was double counting GPU time: it claimed the GPU was
"busy 300% of the time", which is impossible. torch counts each kernel twice, once on the kernel
and once on the operation that launched it. Fixed now (#27). The absolute times above were never
affected.

### KV cache

A KV cache keeps each layer's keys and values from earlier tokens, so generating the next token
only processes the new one instead of re-running the whole window.

A 512-token sample used to take ~108 s. Now it takes **~12 s**, but surprisingly the cache isn't
why: it's ~12 s with or without it (Huang 11.5 vs 13.0 s, RoPE 12.8 vs 12.7 s). The speedup came
from batching the heads. Generating one sample at a time is so little maths per token that the A100
spends its ~23 ms per token on Python and kernel launch overhead, and the cache only saves maths.
On the Mac it did give ~3× (8.5 → 2.6 s), and it should help on the GPU with longer contexts or
many samples at once.

Tests: cached and uncached generation produce exactly the same tokens for every block type, across
the context boundary too.

### Old block vs modern block at ~30M

Five runs, all the same shape: 8 layers, 512 wide, 8 heads, context 2048. Each trained on 205M
tokens (the baseline's amount) at batch 64 and a peak LR of 3e-4, on the fixed val set. Each run adds
one modern piece:

| Run | Params | Val loss | ppl | tokens/s |
|---|---|---|---|---|
| 186M baseline (11-08) | 186M | 3.498 | 33.1 | 22k |
| 1. old block | 34M | 2.684 | 14.65 | 152k |
| 2. + RoPE | 25M | 2.518 | 12.41 | 513k |
| 3. + RMSNorm and QK-norm | 25M | 2.476 | 11.89 | 464k |
| 4. + SwiGLU | 25M | 2.354 | 10.52 | 460k |
| 5. + tied embeddings | 23M | **2.323** | **10.21** | 462k |

Run 5, the full modern block, wins: the lowest loss with the fewest parameters. It's now the
default in the code. Its train loss ended at 1.84.

Two separate things happened here:

1. **The tiny old-block model already crushes the baseline** (3.50 → 2.68) at a sixth of the size.
   Same architecture, different training settings: 3× the learning rate, twice as many optimizer
   steps, and no weight decay on embeddings and norms. So the 186M baseline was most likely
   undertrained. We changed all three at once, so we can't say yet which one mattered most.
2. **The modern block adds another 0.36 on top** (2.68 → 2.32). RoPE and SwiGLU are most of it.

Perplexity 10.21 is just above the sub-10 goal. One caveat: ppl is per token, and our tokens are
BPE merges of several REMI events, so it only compares between models with this same tokenizer.

**Is it overfitting?** Not yet, but it's starting. Val loss improved every single epoch, but the
gap between train and val keeps growing. For run 5 it went from about 0 at epoch 5 to ~0.5 at the
end. 205M tokens is only ~5 passes over our ~43M training tokens, and many of those are
pitch-shifted copies of the same songs. The model is starting to memorise songs on top of learning
general patterns. More data looks like the real lever.
