# 2026-11-08

First proper run after all the Phase 1 fixes, and the first one launched from a script instead of a
notebook. The goal was simple: get a clean baseline number that Phase 2 can try to beat.

### The model

Same 186M model as January: 24 layers, 768 wide, 12 heads, context 2048, vocab 3500, with Huang
relative attention, LayerNorm and GELU (the "old block"). Trained for 50 epochs × 2000 windows,
which is about 205M tokens, at batch 128 and a peak learning rate of 1e-4 with OneCycle.

Colab gave us the 40 GB A100 this time instead of the 80 GB one, so the micro-batch had to drop
from 8 to 4. The effective batch is still 128 thanks to gradient accumulation, so training behaves
the same, it just takes more small steps to get there.

One more change: validation now uses a **fixed** set of 512 windows instead of random ones each
epoch. That makes val loss comparable across epochs and across runs, which we'll need for Phase 2.

### The result

Best val loss **3.498, ppl 33.1**, at the very last epoch. Train loss ended at 3.198. It took about
2¾ hours on the A100, at ~22k tokens/s and an MFU (how much of the GPU's peak maths we actually use)
of about 11%.

```
epoch   0    val 7.727   grad norm 4.77
epoch   5    val 5.361   grad norm 3.90
epoch  14    val 4.245   grad norm 1.95
epoch  30    val 3.646   grad norm 1.33
epoch  49    val 3.498   grad norm 0.86
```

The first few epochs line up almost exactly with the December run (7.73 / 7.17 / 6.78 vs
7.78 / 7.18 / 6.79), so the Phase 1 fixes changed correctness, not how the model learns.
January's 3.46 isn't directly comparable: that was the best of 50 noisy random-window evaluations.
From now on, **3.498 on the fixed val set is the number to beat**.

### Testing it: samples

We sampled four val songs (64-token prompt, 512 new tokens, temperature 0.9, top-k 40, top-p 0.95).
The grammar error rate checks that every note comes with its Pitch, Velocity and Duration tokens:

- .38 Special, Caught Up In You: 0.0% errors, 266 notes
- Joe Walsh, Life's Been Good: 0.1%, 258 notes
- Queen, Under Pressure: 2.6%, 250 notes
- The Beatles, I'm Happy Just To Dance With You: 0.7%, 176 notes

So the model writes well-formed music almost all the time (the 1-epoch smoke model was at 67%).
The catch is speed: **each sample took ~108 s**, because generation reruns the whole window through
all 24 layers for every new token. The MIDI files are in `data/output/baseline-186m/`, still to
listen to.

### Where the GPU time goes

We profiled 10 steps without `torch.compile`. MFU there was only 1.7% against ~12% compiled, so
compile alone buys us about 7×. Attention was by far the most expensive part, roughly 30× the MLP,
because every head runs separately in a Python loop and keeps several 2048 × 2048 score matrices
around for the backward pass. That also means micro-batch 8 runs out of 40 GB.

(The profiler's percentages, "attention is 38% of GPU time" and "GPU busy 32%", turned out to be
off: see 2026-11-12. The overall picture holds.)

That's the shopping list for Phase 2: one batched attention call for all heads, a fused attention
kernel, and a KV cache for generation.

### What broke along the way

A lot, honestly. The highlights:

- Reading 20k small files straight from Drive was painfully slow (~0.2 MB/s), so setup now copies
  the tokens to the VM's own disk first, about a minute.
- The first attempt's VM was killed after ~80 minutes when no browser tab was attached. Keeping a
  tab open fixed it.
- Drive uploads in the background, so after the crash the newest checkpoints hadn't synced yet and
  we resumed from epoch 9 instead of 14.
- Two resume bugs only showed up on a GPU (the RNG state and the checkpoint staying in GPU memory).
  Both fixed, with tests.
- The good news: resume is exact. Re-training epochs 10–14 gave the same val losses to four
  decimals.
- Checkpoints were 6.7 GB each, mostly the per-head causal masks being saved (#26). Saving every 5
  epochs wrote ~80 GB to Drive.

All of these are in `docs/colab.md` under "Gotchas".
